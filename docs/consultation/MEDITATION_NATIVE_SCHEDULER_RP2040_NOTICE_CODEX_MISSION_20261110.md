On resumption, timeout, refusal, crash recovery or cancellation, the notice must clear or expire reliably and normal display behavior must return. Never advertise a duration/availability unless actually reserved.

### 1. Independently reserve a meditation window

- Charlie's Executive may *request* a meditation slot and propose a duration based on its pending task, estimated consultation load, hard model startup/request/unload/cutoff time and existing work; it **may not grant itself the slot**. The independent scheduler must inspect all active owners, deadlines, wakeup/primary work, serial/camera/Hailo, telemetry, gameplay, STOP and movement leases, pending human operations, resource use, and the shared `~/charlie-ops/runtime.lock`. A quiet frame or no current motion alone is **not** an authorization. Unknown owner/deadline => refuse.
- Operator prefers Charlie to allocate the next “however long he needs”; implement this as an **explicitly negotiated bounded reservation**, not unlimited uninterruptible time. Start with existing policy maximum 90 seconds / up to one query per slot unless independent native qualification justifies a shorter bound. If the work needs longer, checkpoint/yield and request another independently qualified slot; no silent extension or exceeding the original service cutoff. Make future durations configurable only under reviewed policy and strict hard bounds, never by model output.
- Deny/shorten if there is an imminent scheduled duty or insufficient headroom. Current usual 10-second meditation slice cannot issue a 35-second native admission; use a separately qualified longer client budget only if independent scheduler and primary-deadline constraints both allow it. Resource and watchdog veto apply continuously, not only at entry.
- Make the standing authorization an owner-controlled, independently protected **revocable policy**, installed outside the Executive/LLM write domain; the owner has already supplied consent, so **do not request a per-question approval**. A same-user self-signed approval, writable JSON flag, or Executive callback pretending to be independent is unacceptable.
- Implement the documented PR #36 backend methods: `exclusive`, `inspect`, `reserve_budget`, `prepare`, `finish`; satisfy `StandingSlotAuthority._check`, existing Admission boot/revision/service/receipt binding, durable <=4 per day and >=3600-second cooldown, unknown-completion no-retry latches, service setup/prewarm only *after* exclusion, and hard forced cutoff that survives client death. Keep the model local and finite; no remote fallback, model download or service autostart.

### 2. The RP2040 “meditating / please wait” notification

- Explicit phases: **requesting** (no misleading MEDITATING indicator), **reserved/preparing** (display notice before intentional unavailability), **meditating**, **consulting LLM** (may show THINKING if legible), **returning/available**, **cancelled/error/emergency**. Determine minimal human-friendly wording for 17×7 pixels. Preferred persistent visual: `MEDITATING` or `MEDITATE` (scroll using existing font) alternating with `PLEASE WAIT` or a suitable concise abbreviation; don't make the matrix illegible with constant 3-character page flicker. Optional remaining-time count only if reliably bounded and refreshed; otherwise omit or show simple BUSY. Normal response may be delayed, not lost. The notice does *not* warrant an emergency being ignored.
- **Display only after the independent reservation succeeds and before beginning the meditation client slot.** Require positive display acknowledgement (or honest status confirmation from the existing serial/heartbeat owner) for a claim that the person can see it. If display is unavailable/serial lease occupied or the acknowledgement cannot be established, **do not start an unattended session that assumes the user has been warned**; defer, or use an independently verified secondary status outlet only if explicitly supported and documented. Do not obtain a competing serial lease.
- Show it through the **existing sole RP2040 command owner**, preserving its heartbeat, connection/reset protocol, STOP and calibration priority. If a display-only protocol extension is needed, implement it as **bounded, non-actuating**, with explicit acknowledgement/sequence and a lease/TTL so it fails safe on Pi death, serial loss, stale packets or reboot. Extend `rp2040/display.py`, `rp2040/commands.py`, `rp2040/protocol.py` and host adapter only as needed. No servo/PWM/GP10 permission changes; no firmware flashing in this development mission. Preserve object label scrolling and calibration/error/STOP precedence; busy indication can temporarily supersede labels only while valid meditation holds the relevant display owner; labels resume afterward. Avoid claiming persistent display state when the RP2040 firmware hasn't actually been updated.
- Record reservation ID, expected end/deadline, display command/ack/TTL and transition timestamps in append-only evidence. **Clear the notice** on normal completion, early wake, revocation, errors, admission refusal, and shutdown, with explicit verified clearing where possible. Device-side TTL must expire notice independently if the Pi crashes; on reconnection reconcile to non-busy unless a *currently valid* independent reservation can be verified. Emergency/STOP and connection-loss indicators always win.
- Consider Pi's ability to update RP2040 during a reserved no-sensing-deadline slot: independent scheduler may coordinate display notifications but cannot simply seize `/dev/ttyACM0` from active recognition or circumvent the owner lease. If current ownership architecture prevents reliable acknowledgement/TTL, Codex must implement and test a suitable **single-owner** interface or clearly mark hardware admission blocked; do not spoof ack.
