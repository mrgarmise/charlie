## 1. Required operational behavior

1. **Normal:** Charlie Pi (`wlan0` or Ethernet) and ELEGOO join a mutually reachable local Wi-Fi/LAN; locate each other by authenticated stable device identity and service discovery, not a fixed `192.168.4.1`. Camera and commands keep existing contracts; component connection status appears in Charlie's existing dashboard/registry rather than a parallel control stack.
2. **Provisioning route priority:** If ELEGOO is already reachable by LAN, use that route. Otherwise, if authorized and `wlan1` is available and can connect to ELEGOO setup AP, use `wlan1` while keeping `wlan0`/Ethernet untouched. If `wlan1` cannot reach it, allow an **explicitly initiated / preauthorized** bounded `wlan0` switch, capture existing connection, provision, restore previous network, and verify it is back. Never require `wlan1`.
3. **Surprise loss:** ELEGOO going offline **must never automatically switch Charlie's primary Wi-Fi, drop its network, change routes, reboot services, or start disruptive recovery**. Mark offline, cease active control traffic, passively rediscover/retry with backoff, preserve Charlie's other functions. Do not infer a lost device merely from lack of internet.
4. **ESP32:** Provide a small secure Wi-Fi provisioning API and a human-usable setup webpage on its AP. Accept authorized credentials and network selection; store in ESP32 persistent storage (NVS) rather than compiling credentials into binary or exposing them in logs; test association and retain recovery AP. Must work on different 2.4 GHz networks. Keep AP available for setup/recovery (AP+STA if practical), documenting shared-radio channel interactions. Do not require internet.
5. **Enrollment/security:** Have an explicit initial trust/pairing procedure (e.g. physical/USB authorization or short-lived setup secret), authenticated per-device provisioning, minimal credential exposure, and safe storage on Pi. No open unauthenticated endpoint that allows anyone on AP/LAN to steal/change credentials. Never log passwords, commit secrets, or include them in test fixtures. Do not assume an arbitrary SSID's password can be obtained automatically; user authorizes new networks.
6. **Two-phase network changes:** Device acknowledges receipt, tries target network, publishes status, and only marks a change successful after Charlie independently rediscovers/authenticates it on the target LAN. Retain or restore a recovery path when unreachable. Keep authoritative state/lease/timeout bounded; distinguish provisioning-success from network join success and verified end-to-end success.
7. **Safety:** Preserve camera HTTP/stream interfaces, SPIFFS resources, existing UART framing and heartbeat handling, Arduino bridge on TCP 100, and authoritative `QualifiedElegooExecutor` safety boundary. Fail closed on active motor-control TCP disconnect/heartbeat loss, even if Wi-Fi association remains up. No automatic motor resumption after reconnect; reconnecting doesn't grant movement authority. Keep approved stationary runtime restrictions intact.
8. **Future-proof:** Define device identity and transport such that the ELEGOO can later be remote on another network via a secure relay/VPN gateway, without building remote control now. Don't force all devices onto a dedicated Charlie hotspot; `wlan1` is only an opportunistic provisioning adapter.

## 2. Implementation deliverables

### A. ESP32 firmware (independent source/branch)
- Confirm compatibility of upstream reference with actual board pins/flash partitions/PSRAM/HTTP routes/UART framing/serial behavior before patching. Prefer official matching ELEGOO source if available. Record provenance, exact upstream commit, toolchain/core versions, and observed differences. Do not assume the UMRT fork is a drop-in firmware replacement.
- Implement modular nonblocking network manager with AP/STA lifecycle, NVS credential handling, authenticated provisioning endpoints, minimal browser setup UI, connection-state query, stable device ID, and bounded recovery logic. Preserve camera, web UI, UART and motor transport behavior. Never hardcode personal home SSID/password or reference fork's custom AP values as production defaults.
- Ensure motor fail-stop is bound to the **actual control-session lifecycle** and heartbeat, not just `WiFi.status()` or AP station count; eliminate accidental active-session break on STA-only connections while retaining safety. Test `FactoryTest()` behavior separately from TCP bridge; its `client` variable may be scoped differently.
- Pin compatible Arduino-ESP32 core / dependencies; include reproducible build instructions. Validate image size fits active app slot and partition table remains compatible; don't overwrite existing NVS/SPIFFS in proposed flashing procedure without clear justification. Keep bootloader/partition table unchanged if possible. Provide build artifact checksum and flashing/rollback runbook for later supervised use, but **do not flash**.

### B. Charlie Pi network manager (isolated development changes)
- Read existing architecture first. Implement a small service/module with explicit state machine: discover → select transport → (authorized) pair/provision → restore primary network as needed → rediscover → authenticate → update device registry/health. Use existing APIs/observability rather than a parallel device/motion registry.
- Separate transport adapter choice from provisioning protocol; do not assume static addresses or device-interface names beyond configurable hints. Prefer system NetworkManager integration with explicit saved-connection handling and rollback timer/lease, but no live network changes in this mission.
- Use a local secret store with restrictive permissions or existing Charlie secret mechanism. Make credentials never appear in git, logs, stdout, telemetry or web responses. Expose status/authorized operations through existing dashboard service layer; ensure a missing ELEGOO never affects Pi's primary connection.
- If `wlan0` switching is requested over a session that depends on `wlan0`, warn about deliberate loss of connectivity and require a separately authorized operation with time-bounded rollback. Do not auto-trigger it from monitoring or startup.
- Preserve existing camera subscriber, sensory bus and qualified executor relationships. Network manager cannot issue independent motor commands.

### C. Tests and acceptance documentation
- Add isolated unit, integration and simulated failure-injection tests for: reachable LAN, available `wlan1`, absent/unreachable `wlan1`, failed `wlan0` restoration, lost ELEGOO, AP channel changes, bad credentials, loss mid-provision, failed authentication, recovery, race/concurrency, stale IPs, interrupted TCP control, no automatic motion, no secret logging.
- Verify no unexpected codepath drops `wlan0`/default route on a missing ELEGOO. Use simulated NetworkManager and ESP32 provisioning endpoints to test complete orchestration. Provide firmware compile and binary-size evidence. If build cannot run in Codex sandbox, provide exact commands and artifacts needed for human execution without claiming it passed.
- Include a clear **hardware acceptance runbook**: build locally; USB flashing only after separate written user authorization; disconnected/free-wheeling motors and car off as appropriate; camera ports 80/81; TCP port 100; serial safe-stop; home Wi-Fi join and dashboard discovery; dual-adapter provision; deliberate one-adapter fallback; rollback to original image; verify device identity before flashing. Actual motion testing requires separate qualification and human supervision.
